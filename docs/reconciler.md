# Reconciler

A cron trigger every 5 minutes runs one pass of the `Reconciler` Durable Object, a singleton.

- **Opt-in registry.** Each time a coordinator reads the workflows it reports the result, with the owning account's id from `GET /repositories/<id>`. The first sighting of a dispatch workflow records the repository's opt-in time, and opting out removes it. Redelivery and catch-up only touch repositories whose account is in `WEBHOOK_ACCOUNTS`. A repository recorded before the account id was stored gets it from `GET /repositories/<id>` at the start of the next pass, once.
- **Redelivery.** It lists the App's webhook deliveries, newest first, down to the newest delivery the last finished scan reached. A scan that hits the limit of 10 pages goes on from the same page in the next pass, so failures behind a burst of `workflow_run` deliveries are still found. Each failed delivery is redelivered at most twice, those not retried yet first. Only deliveries whose first attempt is under 6 hours old, the same limit as for stale comments, for a repository that had opted in by then, are sent again. So failures from before the Worker was ready stay failed.
- **Catch-up.** For each opted-in repository it lists open PRs updated in the last day.
  - A same-repository, non-draft PR goes to its coordinator as a review when its head has no Manki review, no review run in the coordinator that ended in success and no match of a skip rule. Only a review by `manki-review[bot]` counts that is not dismissed, whose body names the head as the reviewed commit, and whose body carries a Manki marker (`<!-- manki`) but not Manki's own `<!-- manki-no-verdict -->`, as Manki decides it. The reviewed commit is read from the body alone, by the rule of Manki's `reviewedCommit`. It is the last line that names a full 40 character commit hash: the commit link of the "About this review" footer (`- Reviewed [...](.../commit/<sha>)`), the head marker (`<!-- manki-auto-approve-head: <sha> -->`) or the `head` of the approval record (`<!-- manki-approval-record: {...} -->`). Manki writes that line below all text it quotes, so an earlier one is quoted text. The commit GitHub reports for a review is never read, because GitHub can move it to the new head after a force push that only rebases the PR. A review whose body names no full commit counts for no commit, so its head is caught up. One of Manki's thread replies is such a review, with an empty body. The no-verdict marker is Manki's own on a line of its own below the review's round record (`<!-- manki-context`), or on any line of its own in a body without a record. Anywhere else it is quoted text, such as a diff line that holds it. A review that was otherwise skipped, dropped, failed, cancelled or deleted does not count, so its head is caught up again, at most once a day.
  - A review that limits stopped names when they lift. Manki writes the time on a line of its own below the round record, as `<!-- manki-retry-after: <ISO 8601 time> -->`, and the catch-up reads it only from Manki's newest review of the head. While that time is ahead, the head is not caught up: it counts as checked until then, at most a day, so no pass asks its coordinator or GitHub about it before then, and `reconciler_catch_up_waits` logs the time. A retry sooner would meet the same limit. A time that has passed, one that is not as JavaScript's `toISOString` writes it, or one above the record, which is quoted text, holds nothing back.
  - PRs opened by a bot are skipped, as Manki does not review them. A bot's push to a person's PR reaches the coordinator, which records the head as handled. If that delivery was lost, the catch-up cannot tell it from a person's push and reviews the head.
- Each pass makes at most 40 calls, counting GitHub and coordinator calls together, within the Free plan's 50 subrequests. The next pass resumes with the next repository.
