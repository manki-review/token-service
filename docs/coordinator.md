# Webhook and PR coordinator

## Receiving deliveries

`POST /webhook` receives the GitHub App's webhook deliveries for Manki's webhook mode. It checks the `X-Hub-Signature-256` HMAC against `WEBHOOK_SECRET`, checks that `X-GitHub-Hook-Installation-Target-ID` is `APP_ID`, and works out where the delivery would go: ignored, the PR's state lane (reviews, a bot's push, thread replies, `check`, `dismiss`, review state checks from reviews and from resolved or reopened threads) its chat lane (explain, questions, remember, forget) or its help lane (`help` on a PR). Work and closes go to the PR's `PrCoordinator` Durable Object before the `202` leaves.

## App events

The GitHub App subscribes to these events. They all arrive at `/webhook`:

| Event | Used for |
|---|---|
| Pull request | Reviews on open, push and ready for review. A close clears the queue, and a merge records the fix rate |
| Pull request review | The review state check (auto-approve) |
| Pull request review comment | Thread replies and thread commands |
| Pull request review thread | The review state check when a thread is resolved or reopened. GitHub Actions has no trigger for this one |
| Issue comment | Review requests, settings box edits, commands and questions |
| Workflow run | The end of a dispatched run. Every other run is ignored |

## Which accounts reach a coordinator

Only repositories owned by an account whose numeric id is in `WEBHOOK_ACCOUNTS` (comma-separated, in `wrangler.toml`) reach a coordinator. That is the account the App is installed on, a user or an organization. Any repository of a listed account works once it opts in as described in [Opt-in and the dispatch workflow](#opt-in-and-the-dispatch-workflow). A delivery for any other account is logged and answered `202` without touching Durable Object storage, so another installation cannot use up the account's daily storage write quota. Look up an account's id with `gh api users/<login> --jq .id`.

## Per-installation cap

Each installation may also store at most 500 comment, review and thread deliveries from people without write access an hour (per clock hour, `INSTALLATION_EVENTS_PER_HOUR` to change it). The `InstallationLimiter` Durable Object, one per installation, counts them. One over the cap is logged and answered `202` without touching a coordinator. Only stored work counts: a delivery the router ignores never reaches the limiter, and the limiter counts a delivery only after its coordinator stored it, so a refused replay writes nothing. `pull_request` deliveries are exempt, because a push to a branch of the repository takes write access and the router already drops fork pushes. A comment or review by a writer, as the [write access lookup](#decisions-without-a-run) settles it, is exempt too, and so is a settings edit (an edit of Manki's comment), a dismissed review and a resolved or reopened thread, which take write access as well. So outsiders can only use up their own share. Run ends are exempt, since dropping one would leave a lane busy. A run end only comes from a run the App started and writes nothing unless it ends a running item. A close that is no merge and finds no queued work writes at most its close time and delivery id, once until the next reopen. A fork's reopen is dropped, so an outsider closing and reopening a PR in a loop costs no storage. Only a stored delivery writes the count, one row each, so a flood above the cap adds no storage writes. `workflow_run` deliveries are dropped unless `manki-review[bot]` sent them, and a body over 25 MiB is refused with `413` while it is read, with or without `Content-Length`.

## Queues and lanes

`PrCoordinator` (one per PR or issue, named `<repository id>:<number>`, SQLite storage) refuses a delivery whose id or body SHA-256 it has seen in the last 7 days (only the id for a thread event, whose body can repeat), queues work per lane, collapses queued pushes into one review of the newest head, a review command into a trusted review command still queued, and the edits of one comment into one item, and drops queued work when the PR closes. Its alarm takes the oldest item of each free lane, except that a queued thread reply goes before a review and before a review state check in the state lane. The review then sees each thread as the reply leaves it, and the check reads the PR when it runs, so it loses nothing while a person waits for the reply. Once replies have gone ahead of a review or a check for 5 minutes, it goes first again. A review that was dispatched before and still holds its [waiting check](waiting-check.md) lets no reply go first. Time the review spent waiting behind a run does not count.

## Opt-in and the dispatch workflow

The alarm then checks that the repository opted in (a dispatch workflow on the default branch and no event-driven Manki workflow next to it, cached for 5 minutes. A workflow file over 64 KB or truncated by GitHub is never parsed and counts as event-driven), and then starts a run of the dispatch workflow on the default branch with `workflow_dispatch`. The dispatch workflow is found by its content: a file in `.github/workflows` that runs only on `workflow_dispatch` and declares all the inputs below. That input set marks it, so it need not name Manki, as manki's own file does not (it runs `uses: ./`). Naming Manki (`uses: manki-review/manki`, the `manki-review[bot]` job `if`, or a local reusable workflow that does) still decides which other files count as event-driven Manki workflows. Name it `manki.yml`. When several files qualify, `manki.yml` goes first, then the first by name. Only that file is dispatched, and `coordinator_opt_in_warning` names the others. The owner, name and default branch come from `GET /repositories/<id>`, read with the opt-in and cached with it, never from the delivery's payload. The inputs follow Manki's dispatch adapter: `event`, `action`, `pr`, `head_sha` (pushes, merges and the approval check of a PR marked ready), `comment_id` or `review_id`, and `delivery_id`. The workflow's `run-name` must be `Manki ${{ inputs.event }}.${{ inputs.action }} on #${{ inputs.pr }} (${{ inputs.delivery_id }})`: the Worker reads the PR from it to route `workflow_run`, and matches the delivery id to find a run whose dispatch response was lost. The token for that call is minted for the one repository with `actions: write` and nothing else, apart from `/token`, which stays capped.

## Tracking runs

A lane stays busy until the `workflow_run` webhook reports the run's end. A poll every 2 minutes is the safety net: it ends items whose run completed or was deleted, and cancels runs still queued after 30 minutes or running after 40. An item whose run never started is queued again once. A run not seen ending 75 minutes after its dispatch is cancelled, and its lane stays busy until the cancel succeeds or the run is seen completed. When it cancels a review's run that started, for running past 40 minutes or at that deadline, the Worker ends the run's progress comment and in-progress `Manki` check itself as for a Cancel tick, since the run's post step can no longer mint a token. They say "Review stopped:" and why, such as "it ran longer than 40 minutes".

## Retries

A token mint that fails with a 5xx, a 429, a rate limit or a network error is retried with the same backoff as a failed start. A failed start is retried after 2, 4, 8 and then every 16 minutes. An item with no dispatch attempt waits for it in the queue, so a newer push merges into it instead of queueing behind it. Only a 403 that is no rate limit (by its headers or its message), a 404 or a 422 counts as a refusal. Failed dispatches retry after 15 seconds, 1 minute and 5 minutes, and a retry first looks for a run the earlier attempt started.

## Trust

A comment or review counts as trusted when its author's `author_association` is `OWNER`, `MEMBER`, `COLLABORATOR` or `CONTRIBUTOR`, or its sender opened the PR, as Manki's own check decides it. An outsider's review never replaces the trigger of a trusted review state check, and a review whose sender is not known as a writer never replaces a writer's. A writer's review or thread change takes over a trigger not known as a writer's, so the check never runs under the name of a sender the lookup would refuse. An untrusted review request queues on its own and never merges with a push review.

## Reactions and the subrequest budget

A Manki command whose sender wrote it and has write access gets the eyes reaction in the alarm right after it is queued, so the commenter sees it before the run starts. So does a writer's reply without a command in one of Manki's review threads, also while a review of the PR runs. The payload does not say whose thread it is, so the alarm reads the comment the reply answers, one `GET` per such reply, and reacts only when Manki wrote that comment, it carries a Manki marker (`<!-- manki`) and it is the first of its thread. One alarm spends at most 18 GitHub calls on reactions, a command's costing one and a reply's two, so a burst of replies leaves the dispatch its share of the Free plan's 50 subrequests. The comments past that get their reaction in the next alarm, which is set at once. The lanes get what the waiting reactions leave of the 50, and every call they make is counted, with token mints and the opt-in read. They go one after another, state, chat, help and settings, and a lane polls its run, ends a waiting check or starts its next item only while the costliest path of that step still fits: 32 calls, or 11 for an item that only dispatches a run, answers help or ends a bot's push. A step that does not fit waits for the next alarm, which is set at once and begins with the lane that waited, so no work is dropped and none fails on the limit. Lanes that start a run in the same alarm share one minted `actions: write` token. The reaction's token holds only `issues: write` and `pull_requests: write` for a PR or issue comment, or `pull_requests: write` alone for a review comment, on the one repository. Only an opted-in repository with dispatch on gets the reaction, and a failed reaction is logged and leaves the queue alone.

## Hourly dispatch caps

Each lane allows 30 dispatches per hour for trusted work and 5 for untrusted work, counted apart. A trusted review or merge over the cap waits until the hour allows it. Any other work over the cap is dropped. Installation tokens are cached in memory per permission set until 5 minutes before they expire.

## Storage lifetime

The coordinator deletes its storage a week after the PR closed, or 90 days after the last delivery of a PR it never saw close, and never while an item is queued, dispatching or running. A reopen, or work queued after the close such as a comment, counts the PR as open again. A reopen records its time, also for a PR without state, and a close whose `closed_at` is older is a late redelivery and changes nothing, even once its delivery id is forgotten. A run's end after the close does not.

## Skip rules

Before a review from a push starts, the coordinator reads `skip_labels`, `skip_authors` and `skip_branches` from `.manki.yml` on the PR's base branch, so a PR cannot skip itself. A PR that matches one gets no run: the Worker completes a `Manki` check on its head as `skipped` and posts no comment. The rules match as in Manki. Labels and authors match in any case, and branches as globs on the head branch. An author rule also needs the push's sender to be a listed author, since a writer can push to a bot's PR. When the PR's head is no longer the queued push's, or for a catch-up, the pusher is unknown and no author rule matches. Label and branch rules never match a fork's head. A missing file, one over 64 KB, one that does not parse, or rules that are not lists of non-empty strings skip nothing. A review request by comment ignores the rules. The Worker only reads `.manki.yml`, so a workflow with another `config_path` gets its skips from the Action, after a run starts. A skipped head counts as handled, so neither the cron nor a redelivered push reviews it again. The check needs `checks: write` on the installation. Without it the PR is still skipped, without the check.

## Conflicts with the base branch

Before any review starts, push or request, the coordinator also reads the PR's mergeability. When GitHub says it conflicts with its base (`mergeable: false` or `mergeable_state: dirty`), no run starts. The Worker posts one note, "This PR conflicts with `<base>`. Rebase it, and Manki reviews it then.", marked `<!-- manki-conflict-note -->`. A later skip edits that note instead of adding another, and Manki deletes it once a review posts. The Worker also completes a `Manki` check on the head as `action_required` with the title "Rebase needed". The item ends `skipped` with conclusion `conflict`, which `coordinator_finished` logs, and the cron leaves that head alone. While GitHub has not computed mergeability (`mergeable: null`), the review waits 5 and then 15 seconds and reads the PR again, then starts as before. A retry after a dispatch attempt skips none of this. The note's token holds `issues: write` and `pull_requests: write`, since GitHub needs `pull_requests: write` to comment on a pull request. The check needs `checks: write`. A note that fails to post is logged as `coordinator_conflict_note_failed`, and the item still ends skipped. A GitHub failure while creating the check is retried after the usual backoff, and the retry checks the conflict again, since no dispatch was tried.

## Drafts

Drafts get no automatic review. A push to a draft, or a draft opened, is still queued, and before its review starts the coordinator drops it unless `.manki.yml` on the base branch sets `drafts: review`. Any other value, or no file, skips drafts, as in Manki. Marking the PR ready for review starts a normal review when its head has no review yet, and otherwise queues the approval check described below. Converting it back to a draft stops automatic reviews again. Comments, replies and the Review this draft box still run on a draft. The cron never catches up a draft, even with `drafts: review`.

## One review per head commit

A commit has one `Manki` status, however many pull requests have it as their head. So Manki reviews one pull request per head commit: of the repository's open pull requests whose head is that commit, on a branch of the repository itself, only the one with the lowest number. Take one branch opened into `main` as #10 and into `release` as #11. #10 is reviewed. #11 gets no run and no `Manki` check of its own, so the check it shows is the one of #10. Without the rule both would be reviewed, and whichever finished first would show its result on both while the other was still reviewing. Before any review starts (a push, an opened or ready pull request, a review command, a review box or a catch-up), the coordinator lists the pull requests of the head with `GET /repos/{owner}/{repo}/commits/{sha}/pulls`, on the first dispatch attempt and after a draft is dropped. GitHub also lists a pull request that only contains the commit, such as one stacked on the branch, and that one does not count. Every held request tells the pull request. Manki's settings comments get the status line "not reviewed, #10 has the same head commit", and the box that asked is unticked each time: on the newest settings comment and on the one the box was ticked on. Without a settings comment the Worker posts one note per head, marked `<!-- manki-conflict-note -->`, which names #10 and says how to get a review. A review command gets that note each time, as a new comment below the command, and the older note is deleted. A report that fails is logged as `coordinator_yielded_report_failed`, and the review is still held. The item ends `skipped` with no conclusion, so the head does not count as handled and each later request checks the rule again. The rule only ever holds a review back. When the list call fails, when its reply is not a list of pull requests, when it returns a full page of 100 that may be cut off, or when it does not name the pull request itself, the review runs as without the rule and `coordinator_head_pulls_unsure` logs why. Nothing starts the held review on its own when the lower pull request closes or moves to another commit: a review command, a review box or a push to the held pull request does. The lower pull request holds the other one while it is open, also as a draft, paused, skipped or in conflict. Thread replies, other commands and review state checks are not held. A pull request from a fork is neither held nor counted, since only a head on a branch of the repository counts.

## Bot pushes

Manki does not review a bot's push. A `pull_request` delivery whose sender is a bot, for a PR opened, pushed to or marked ready, starts no run. The coordinator records its head as handled, so the cron leaves it alone, and queues the push in the state lane, where it waits behind a run like any other work. There it reads the skip rules as for a person's push, with the bot as the sender an author rule needs. When the PR matches a rule, the Worker completes the `Manki` check on the pushed commit as `skipped`. So `skip_authors: ["dependabot[bot]"]` lets a required `Manki` check pass on that bot's own PRs, while a person's push to one of them is still reviewed. GitHub reads the `Manki` check created last on a commit, so the skipped check is added only where it cannot hide another: the pushed commit is still the head of the open PR, no pull request with a lower number is reviewed for the same head, and the commit holds no `Manki` check of the App. A list of those checks that fails is retried with the start backoff. A draft gets no check either, unless the base config sets `drafts: review`. A bot's push that matches no rule gets no review and no check. On a repository that requires the `Manki` check, such a PR waits until someone asks for a review by comment or a skip rule covers it.

## Ready for review

A PR marked ready (`pull_request.ready_for_review`) queues a review like a push, unless its head already has one. The review of a draft holds its approval, so once a review run of the head ended in success, the coordinator queues an approval check instead of dropping the event: a `review_state` item that is dispatched as event `pull_request` with action `approval_check` and the head in `head_sha`. Manki answers that action with its approval check on that head and starts no review for it, and a Manki version that does not know the action ignores the run. A review counts by the head its push was queued for or by the commit its run was started for, so a review asked for by a settings box or a command counts too. While a review of the head is queued or running, the check is queued behind it. It starts only after that review has ended, since the lane starts its oldest queued item, only a thread reply goes ahead of an older item, and nothing starts while an item is under way. The check is a review state check like the one of a resolved thread: no pause, skip rule or draft setting stops it, it reads no config and it gets no waiting check. It joins a queued check only when that one runs after the review, and no other head's change joins it, since Manki runs it only while its head is the PR's. A head that a skip rule, a Cancel tick or a conflict handled has no review, so marking the PR ready there starts nothing. A late `opened` or push delivery of a reviewed head is still dropped, so no head is reviewed twice.

## Decisions without a run

Some decisions need no model, so the coordinator makes them without a run:

- **Help.** `@manki help` on a PR, in a comment or a review comment, is answered by the coordinator itself with Manki's command table and a thumbs-up on the command. It has its own lane, so it never waits behind a run. Its token holds only `issues: write` and `pull_requests: write` on the one repository. A reply that fails to post is retried with the start backoff.
- **Write access.** Manki only acts on a comment or submitted review whose sender has write access. The webhook handler settles it before the work is queued, for a comment or review its sender wrote. An `OWNER` has it. Anyone else is looked up with `GET /repos/{owner}/{repo}/collaborators/{login}/permission`, with a `writer_check` token holding `metadata: read`, since a read-only member shows as `MEMBER`, a read-only outside collaborator as `COLLABORATOR`, and a member with private membership as `NONE`, `CONTRIBUTOR` or even `FIRST_TIME_CONTRIBUTOR`. Only `admin` or `write` counts, and a writer counts as trusted too. The answer is reused for 5 minutes per installation, repository and login. A failed lookup counts as no write access and is not reused. A comment or review item still not known as a writer, or an edit of someone else's comment, has its sender looked up again before it starts. Without `admin` or `write` it ends skipped and starts no run. Such an item can neither take over a queued push review nor take on its head, so a refused comment never costs the push its review.
- **Pause.** While the PR's reported `pause` is set, a review from a push, a ready for review or a catch-up ends skipped. The draft and skip rules above go first, so a draft is still dropped and a PR that matches a skip rule still gets its skipped check. Like them, a pause skips only before the first dispatch attempt, since a later try may find that attempt's run. Everything a person asks for still runs: a settings box review, a review request, thread replies, other commands and review state checks, so resolving the last thread can still lead to an approval. The skipped head gets one `Manki` check, completed as `action_required` with the title "Automatic review paused" and a link to the PR. Its summary gives the reported reason or names the Pause box, and says what reviews the commit: Review again, or unticking Pause when only the box pauses. The Worker also sets the status line of Manki's newest settings comment, among the PR's newest 100 comments, to "automatic review paused, `<sha>` waits". It lists those comments without their bodies, since anyone can fill one, and reads only the bodies of Manki's 5 newest. A settings comment whose review is still in progress belongs to its run and is left alone. The check needs `checks: write` and the comment edit `issues: write` and `pull_requests: write`. A failure in either is logged as `coordinator_paused_report_failed` and the review is still skipped. A check that failed to post is posted by the next skip of that head, such as a catch-up.
